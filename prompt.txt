# SCAMTASTIC STUDIO — PHASE 1
## Compact Node-Based Creation System

Act as a senior full-stack engineer working directly in the existing Scamtastic repository.

Your task is to implement the first functional version of Scamtastic Studio: a compact, extensible, node-based project editor that will eventually power Visual Studio, Logic Studio, and Game Studio.

This is a real implementation task, not a mockup. Inspect the repository first, understand its architecture, and integrate with existing conventions.

## 1. Repository safety

- Work exclusively on the `development` branch.
- Never switch to, modify, merge into, or deploy `main`.
- Inspect the working tree before making changes. Preserve existing user changes.
- Do not reset, force-push, or discard user work.
- Inspect existing routes, authentication helpers, Supabase clients, authorization patterns, database migrations, tests, and CSS before designing the implementation.
- Reuse established project conventions wherever practical.
- Do not rewrite unrelated features.
- Do not introduce a second authentication system or duplicate existing infrastructure.
- Do not claim that migrations have been applied. Database migrations must be reviewed and applied manually to the development Supabase project.

## 2. First inspect, then plan

Before modifying files:

1. Inspect `package.json`, the application structure, existing project and profile routes, Supabase integration, CSS, and tests.
2. Identify how authenticated users access existing features.
3. Identify existing database naming conventions, migration history, and Row Level Security policies.
4. Determine which existing UI components and design tokens can be reused.
5. Present a concise implementation plan and identify any architectural conflicts.

Then implement the smallest coherent vertical slice that fits the existing architecture. Do not stop after producing a plan unless a genuine blocker requires a decision.

## 3. Compact project representation

Create a strongly typed, versioned project graph format.

Requirements:

- Each project has a stable ID.
- Each node has a stable ID within its graph.
- Nodes reference registered node types rather than embedding executable implementations.
- Nodes contain only explicitly overridden parameters where practical.
- Connections reference node IDs and registered input/output port IDs.
- Graphs identify their schema version.
- Serialization is deterministic where practical.
- Reject malformed, excessively large, or unsupported graph data.
- Validate node types, parameter types, port compatibility, connection targets, duplicate IDs, and resource limits.
- Never execute arbitrary JavaScript or user-provided source code.
- Never use `eval`, `new Function`, or equivalent dynamic code execution.
- Make future schema migrations possible without silently corrupting existing projects.

Use a readable serialized representation initially. Add compression only when measurements justify its complexity. Do not optimize by sacrificing correctness or maintainability.

Do not duplicate node implementation code inside each project. Node implementations must live in a shared, registered runtime.

## 4. Reusable graph engine

Implement the core engine independently of the editor UI.

Provide clear, typed interfaces for:

- Graph and node definitions.
- Node type registration.
- Typed input and output ports.
- Graph validation.
- Deterministic serialization and deserialization.
- Safe evaluation of supported nodes.
- Resource limits.
- Schema-version handling.

Separate graph data from React components so future editors and runtime consumers can reuse the same engine.

Evaluation must operate only on registered node implementations and supported operations. Detect invalid dependencies and cycles. Reject cycles unless a specific node type and execution strategy explicitly support them.

Keep the architecture extensible for future visual, logic, and game nodes without implementing all three studios now.

## 5. First functional node library

Start with a small visual-oriented demonstration library, not dozens of unfinished nodes.

Implement at least:

- A constant/color value node.
- A background or surface node.
- A supported visual-effect or style-setting node, if it fits the existing application architecture.

If a proposed node cannot be safely evaluated or displayed in the current application, do not fake its behavior. Choose a smaller real implementation and document the limitation.

Use registered metadata for node labels, categories, ports, defaults, and supported parameters.

## 6. Node-editor interface

Create an authenticated Studio interface using Scamtastic's existing design system.

The first editor should support:

- Creating a project.
- Opening a project.
- Adding supported nodes from a node library.
- Selecting and moving nodes.
- Creating and removing connections.
- Editing node parameters.
- Deleting nodes.
- Seeing validation errors.
- Previewing the actual result of the supported graph.
- Saving and reopening a project.
- Undoing and redoing common graph edits, if feasible within the first slice.

The interface must be usable on desktop and adapt reasonably to smaller screens.

Do not spend the first milestone polishing animations or building a huge component library. Prioritize reliable interaction and correctness.

Do not add fake Save, Publish, Purchase, or Marketplace buttons that appear to work without implementing the underlying behavior.

## 7. Storage efficiency

Storage efficiency is a core requirement.

- Keep small graphs compact.
- Reference registered node implementations instead of copying them.
- Store only overridden defaults where practical.
- Avoid saving a complete duplicate on every edit.
- Do not duplicate shared built-in assets.
- Enforce reasonable limits on graph size, node count, and supported parameters.
- Avoid downloading large dependencies when native browser or existing project capabilities suffice.
- Do not store transient editor state unless it is necessary for recovery.
- Do not store previews or generated output when it can be safely regenerated.
- Do not introduce a separate storage provider without a demonstrated need.

Measure the actual serialized size of sample projects and document the result. Do not invent performance or storage benchmarks.

## 8. Persistence and permissions

Inspect the existing Supabase schema and authorization architecture before designing persistence.

Implement real project persistence only if it can be integrated safely with the existing system.

Requirements:

- Every project has an owner.
- Only authorized owners or collaborators may read or edit private projects.
- Public output must never expose private draft graphs or unpublished assets.
- Enforce authorization on the server and in database policies as appropriate.
- Never trust a client-provided owner ID.
- Never expose service-role credentials to the browser.
- Validate graph data on the server before saving.
- Avoid storing large graph payloads in relational tables if the repository's architecture and measurements indicate object storage is more appropriate.
- Do not add purchases, currency transactions, marketplace listings, or collaboration features in this milestone.
- Do not fabricate persistence if the database integration is not ready.

If schema changes are necessary, create a reviewed migration file following the repository's exact naming and migration conventions. Preserve existing data. Never apply the migration automatically.

If safe persistence cannot be completed in this milestone, implement a clearly isolated persistence interface and report precisely what remains unfinished. Do not pretend local-only storage is server persistence.

## 9. Testing

Add automated tests for the graph engine.

At minimum, test:

- Valid graph serialization and deserialization.
- Preservation of node parameters and connections.
- Rejection of malformed data.
- Rejection of unknown node types.
- Rejection of incompatible connections.
- Detection of duplicate IDs.
- Graph-size and node-count limits.
- Unsupported schema versions.
- Cycle detection.
- Safe evaluation of supported nodes.
- Deterministic output where applicable.

Use the repository's existing test framework. Add dependencies only if necessary and explain why.

Run the relevant tests, TypeScript checks, and production build when possible. Fix regressions introduced by your changes.

## 10. Visual design

Reuse Scamtastic's established dark slate interface.

Use the existing purple accent palette where appropriate, with cyan and magenta reserved for the glitch identity and supporting highlights.

The editor should feel like a cohesive Scamtastic product, not an unrelated third-party application.

Prefer existing CSS and components over introducing a new styling framework.

## 11. Scope boundaries

Do not implement these yet:

- A complete Logic Studio.
- A complete Game Studio.
- Arbitrary user code execution.
- A full marketplace or storefront.
- Real-money purchases or transactions.
- A complex collaborative merge system.
- A large collection of unfinished nodes.
- Automatic database migration execution.
- Production deployment or changes to `main`.

Prepare the architecture for these possibilities without building them prematurely.

## 12. Completion report

When finished, report:

1. What was implemented.
2. Which files were added or changed.
3. How to access the Studio.
4. How graph data is represented and how small a representative graph actually is.
5. How persistence and authorization work.
6. Which database migrations need manual review or application.
7. Which tests, type checks, and builds passed or failed.
8. What remains unfinished.
9. Any security or architectural limitations.

Do not claim success for any test, build, migration, or feature that was not actually verified.

The priority is a small, correct, extensible foundation that we can confidently build upon.
